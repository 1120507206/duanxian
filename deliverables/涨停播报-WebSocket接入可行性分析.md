# 涨停播报接入 WebSocket 可行性分析

> 分析日期：2026-10-16
> 对照项目：`D:\code\duanxianxai-vue3\new-vue3`（旧站）
> 目标项目：`D:\code\duanxian`（当前短线侠）

---

## 一、结论先说

**可以接，而且是直连就行 —— 不需要对方配合、不需要鉴权、不存在跨域拦截。**

我做了三轮实测（详见第三节），关键结论：

| 验证项 | 结果 |
|---|---|
| 原站 WS 地址是否可连 | ✅ 可连，握手 ~180ms |
| 浏览器跨域（从我们的域名连） | ✅ **不校验 Origin**，直接建连成功 |
| 是否需要 token / 登录 | ✅ 不需要，裸连即可 |
| 是否 wss 加密 | ✅ 是，https 站点不会被混合内容拦截 |
| 通达信内核（Chrome 81）是否支持 | ✅ 原生支持 WebSocket |

唯一的"不确定性"不是能不能连，而是**要不要在前端直连**——这涉及权益门控和音源防盗用，见第五、六节。

---

## 二、现状：我们到底丢了什么

旧站的涨停播报是**双源互补**的架构，我们只搬了一半：

```
                        ┌──────────────────────────────┐
                        │  旧站 duanxianxai-vue3        │
                        └──────────────────────────────┘
        数据源 A（事件流）                     数据源 B（全量状态）
   wss://m.duanxianxia.com/wss3          ztlive_all.json（约 3s 重写）
   from=ztpool 封板推送                   全量涨停列表 / 统计 / 板块
   ★ 自带 readurl 音频地址                ✗ 不含音频
   → 即时播报 + 行置顶 + 闪烁             → 表格全貌 + 统计
        ↓                                      ↓
        └─────────────── 合并 ─────────────────┘
                          ↓
                  表格 / 语音播报 / 统计

                        ┌──────────────────────────────┐
                        │  当前 duanxian（只有 B）       │
                        └──────────────────────────────┘
                                ztlive_all.json
                         后端代理 + 1.5s 缓存窗口 + 单飞
                         前端 3s 轮询（隐藏页降频 10s）
                                 ↓
                    前端靠"快照增量对比"反推封板事件
                          → 语音播报（TTS 合成音）
```

### 差异对照表

| 维度 | 旧站 | 当前项目 | 差距 |
|---|---|---|---|
| 封板事件来源 | WS 推送（瞬时） | 快照增量反推 | 本质差别 |
| 播报延迟 | 封板瞬间（~0s） | 3~6s（轮询周期 + CDN 3s 缓存） | 打板场景体感明显 |
| 是否可能漏播 | 基本不会 | **会**：两帧之间封板又炸板的会丢 | 结构性缺陷 |
| 音频音源 | 原站 mp3（readurl） | 浏览器 TTS 合成 | 音色差一档 |
| 表格新行置顶 | 推送即置顶 + 闪烁 | 等下一轮快照 | 观感滞后 |
| 页面后台时 | WS 不受定时器节流 | 定时器被节流到 10s+ | 后台及时性差 |

> 代码里已经预留了 `readurl` 分支（`useZtVoice.js` 的 `playAudioUrl`），注释写着"当前后端快照还不带 readurl，字段一到位就自动生效"。**而快照永远不会有 readurl —— 这个字段只在 WS 推送里有。** 所以不接 WS，这个预留分支就永远激活不了。

## 三、实测证据

### 3.1 Node 侧直连（验证服务可用）

```
[OPEN] wss://m.duanxianxia.com/wss3   in 205 ms
[OPEN] wss://ws.duanxianxia.com/wss3  in 204 ms
（12 秒内 0 条报文）
```

两个地址都通。0 条报文是**正常的** —— `ztpool` 是封板事件流，不是心跳流，实测"几分钟 0 条"是常态。

### 3.2 真实浏览器跨域实测（决定性证据）

从我们的页面源 `http://localhost:3000`（跨域）发起连接：

```json
{"origin":"http://localhost:3000",
 "url":"wss://m.duanxianxia.com/wss3",
 "opened":true, "openMs":170, "timeout":true}
```

**`opened: true`** —— 浏览器一定会带 `Origin` 头，服务端没有拒绝，连接保持 10 秒直到我们主动超时关闭。这证明**前端可以直接连，无需任何后端中转或代理**。

### 3.3 上游快照字段核查

```
curl https://ds.duanxianxia.com/vendor/stockdata/ztlive_all.json | grep readurl
→ 空
```

确认：**快照不含任何音频字段**。音源（`readurl`）只有 WS 推送携带，值是一个 mp3 短 hash，前端拼成
`https://bm.duanxianxia.com/static/upload/read/{hash}.mp3` 播放。

### 3.4 报文结构（从旧站代码提取）

WS 地址：
- 常规：`wss://m.duanxianxia.com/wss3`，重连失败切 `wss://ws.duanxianxia.com/wss3`
- 免费域名（`bm.` 子域）：`wss://free.duanxianxia.com/wss1`

连接方式：`new WebSocket(url)` —— **无 query、无 header、无 token**。

报文是 JSON，同一个连接上跑两个频道，靠 `from` 字段分流：

| `from` | 含义 | 谁处理 |
|---|---|---|
| `ztpool` | 封板事件（我们要的） | ZtLive.vue |
| `ztyd` | 异动事件 | Yidong.vue |

先按关键词 `stocklive` 粗筛，再按 `from` 分流。`ztpool` 报文携带字段大致为：
`{from, code, name, status, ban, ztyy, ztnum, ftime, etime, readurl, ...}`

## 四、为什么值得接

1. **体验补全**：把"秒级"升到"瞬时"，这是产品从"能用"到"好用"的分水岭。
2. **激活音源条款**：唯一能拿到原站 mp3 音色的路径，比 TTS 合成强一档 —— 也是**付费的第二理由**（第一理由是"实时性"）。
3. **补齐结构性缺陷**：轮询反推事件会漏（封板即炸板），WS 事件流不会漏。
4. **后台也准点**：网络事件不受浏览器定时器节流影响，切到后台/其它标签页仍能准点播报。
5. **商业化方案里已经排期**：`涨停播报-商业化与获客方案.md` 把"WebSocket 即时推送"列为 P3 / 付费理由。

## 五、三种接入方案

### 方案 A：前端直连（最快，1~2 天）

新增 `composables/useZtliveSocket.js`（移植旧站 `useSharedWebSocket.js` 的思路），在
`Ztlive.vue` 与 `ZtliveEmbed.vue` 各挂一个订阅；收到 `from='ztpool'` 时 ① 立即触发语音播报
② 该行 unshift 到顶部并打闪。**快照轮询保留**（提供全量 + 兜底）。

- ✅ 改动集中在 2~3 个文件，当天可验证
- ✅ 旧站现成代码可直接移植（`useWebSocket` / `useSharedWebSocket` 已封装好心跳、重连、多订阅共享）
- ❌ WS 地址暴露在前端（但旧站也这样，非新增风险）
- ❌ **无法做权益门控** —— 事件流会直接进浏览器，免费用户也能拿到

### 方案 B：后端中转（推荐，2~3 天）

后端用 `ws` 库作为 client 连原站 → 通过 **SSE** 或**我们自己的 WS** 推给前端。
前端只连自己的域名。

```
原站 wss3 ──(后端 ws client)──> 我们的后端 ──(SSE / 自建 WS)──> 前端
                                        │
                                  权益门控在这里做
```

- ✅ 前端只连自己的域名，不受原站策略变化影响（对方哪天加 Origin 白名单，方案 A 立刻挂）
- ✅ **可在服务端做权益门控**：未付费用户不下发事件流，防止白嫖
- ✅ 断线重连 / 多实例复用 / 连接数控制 由服务端统一
- ✅ 音频也可以判断后决定是否下发 readurl
- ❌ 多一跳，复杂一点；需引入 `ws` 依赖

### 方案 C：混合

事件用后端中转（B 的稳健性），音频直接播原站 mp3（省一跳）。实务上等价于方案 B 的简化版。

### 方案对比

| | 改动量 | 权益门控 | 抗原站策略变化 | 推荐度 |
|---|---|---|---|---|
| A 前端直连 | 小 | ✗ | ✗ | 验证阶段 |
| B 后端中转 | 中 | ✓ | ✓ | **正式上线** |
| C 混合 | 中 | ✓ | ✓ | 可选 |

## 六、需要注意的坑

1. **重复播报**：WS 事件 + 快照增量两条都在跑，同一只票会被播两遍。
   必须确立"**以 WS 为准，快照只做全量校正、不触发播报**"的口径。旧站的做法是：快照只"播种"不播报，只有新增才出声 —— 接 WS 后要改成"WS 播报，快照不播报"。

2. **封板 / 炸板语义**：`ztpool` 推送是**封板权威事件**。旧站代码明确警告：
   "勿用 fund 推导的 statusText 过滤（推送时 fund 常未到）"。照搬我们的 `normalizeRow` 逻辑要小心。

3. **快照尚未收录的竞态**：推送到达时（封板瞬间），快照还没收录这只票。旧站为此做了 `pendingPushRows` **保护期**（登记新行，快照未收录期间并回列表，收录或超时后让位），否则下一轮快照会把刚置顶的行整体替换掉。这个机制必须一起移植。

4. **断线重连 + 心跳**：需 30s ping 心跳 + 3s 重连延迟 + 失败切备用地址。旧站的 `useSharedWebSocket` 已封装（含"多组件共享一条物理连接"），可直接移植。

5. **后台标签页**：轮询会被节流，WS 不会。但要注意"运行态暂停"时（如尾盘冻结、主题切换）应有 `shouldReconnect: () => runtimeActive` 之类的地方闸门，避免无意义重连。

6. **通达信独立页同样要接**：旧站的 TDX 版（`src/tdx/ztlive.js`）是**独立连的**，不走 composable。我们两个入口共用 `useZtliveFeed`，接入时最好也共用一份 socket composable，避免两套逻辑。

7. **域名归属**：`duanxianxia.com` 是你自己的旧站域名，不是第三方数据商，无授权风险。（若将来换外部供应商，才需要重新评估授权与 Origin 白名单。）

---

## 七、建议

**如果只是想快速验证效果** → 先上**方案 A**，移植旧站的两个 composable，半天就能看到"封板瞬间出声"。

**如果是正式上线** → 走**方案 B**，把事件流收在后端：
- 前端保持"只连自己域名"的单一网络边界，将来对方改策略也不慌；
- 权益门控落在服务端，语音实时播报成为可收费的能力；
- 音频音源是否下发也由服务端控制，防止白嫖。

无论哪种方案，**快照轮询都必须保留**（全量列表、统计、冷启动兜底），WS 只负责"事件"这一层。
